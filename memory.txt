2. WHAT THE PROJECT IS
------------------------------------------------------------------------
An internal web-based communication & collaboration platform for
organizations (a focused alternative to large enterprise tools), built to
**Slack-parity behavior** for all in-scope features and supporting
**multiple organizations (multi-tenancy)**.

Core capabilities (MVP): authentication, profiles/status, roles,
MULTIPLE organizations + switching, public/private channels, channel
membership, topics/purposes + channel notification prefs, real-time
messages, 1:1 and group direct messages, message edit/delete, THREADS,
reactions, mentions (@user/@channel/@here), file/media attachments,
pins + saved items, search (with operators), notifications, unread counts,
presence (ACTIVE/AWAY/DND/OFFLINE), typing indicators, drafts, member
directory, admin + audit logs, responsive UI, light/dark mode.

Out of scope for MVP: cross-organization federation (Slack Connect),
SSO/SAML/SCIM, voice/video, apps/marketplace/workflow automation,
compliance/eDiscovery, Slack-AI-style features, mobile apps.

Full details: project.md (SRS **v1.2**, see sections 59-60) and
phases.txt (v2.0). Target scope = all project.md features at Slack
behavior + multi-org.

3. CHOSEN TECHNOLOGY STACK
------------------------------------------------------------------------
Frontend : Next.js (App Router) + React + TypeScript + Tailwind CSS
           + Socket.IO client        (folder: frontend/)
Backend  : Node.js + Express + JAVASCRIPT (CommonJS) + Socket.IO
                                       (folder: backend/)
Database : MongoDB + Mongoose (document database)
Storage  : Cloudinary (files/media/avatars; NEVER stored in MongoDB).
           Avatar upload uses Cloudinary SIGNED DIRECT UPLOAD: backend
           only issues a signature, frontend uploads directly, backend
           stores the returned publicId/url.
Cache    : NONE. Redis is intentionally NOT used. Realtime presence and
           typing state are in-memory on a single backend instance.
           Rate limiting is also in-memory.
Auth     : Password hashing with Node built-in crypto.scrypt (salt +
           timing-safe compare). NO bcrypt dependency.
           Session strategy: opaque 256-bit random token; only its
           sha256 hash is stored in the Session collection. The raw
           token travels in an HMAC-SHA256 signed, HttpOnly, SameSite=Lax
           cookie (name from COOKIE_NAME, default "sid"). Cookies are
           implemented with Node crypto (NO cookie-parser dependency).
           Session TTL default 7 days; TTL index auto-expires documents.
Email    : Optional. A mail util lazily requires "nodemailer" (declared
           in package.json but NOT installed yet). If nodemailer or the
           EMAIL_* config is missing, password-reset links are logged in
           non-production instead of emailed.
Deploy   : Linux/container + reverse proxy + HTTPS + managed MongoDB.
Tenancy  : MULTI-ORGANIZATION (multi-tenancy). Users are global
           identities; role/membership is per organization via
           OrganizationMember; every tenant document carries
           organizationId; each session carries activeOrganizationId.
           See project.md section 59 and the multi-tenancy checklist in
           phases.txt. STRICT tenant isolation is mandatory on all reads
           and writes.

5. CONVENTIONS
------------------------------------------------------------------------
- Backend language: JavaScript (CommonJS: require / module.exports).
  Frontend language: TypeScript.
- Backend layering: routes -> controllers -> services -> models.
- Small files, single responsibility, reuse via utils/services.
- Errors: throw new AppError(statusCode, message). Async route handlers
  are wrapped with asyncHandler(); the central errorHandler formats the
  JSON response ({ success:false, message }); 500 details hidden in prod.
- Responses: controllers use success(res, data, statusCode) ->
  { success:true, data }.
- Avoid new dependencies: prefer Node built-ins (crypto) for password
  hashing and cookies. Only express/mongoose/socket.io/cloudinary/helmet/
  cors/dotenv are installed; nodemailer is declared but not installed.
- API base path: /api (e.g. http://localhost:5000/api).
- Backend port default 5000 (matches .env; frontend env points to 5000).
- No dependency installation performed by the AI ([R4]).
- No test scripts written ([R2]). Files are syntax-checked with
  `node --check`; modules smoke-loaded with `node -e` only.
- STYLING (see DESIGN.md): font is Poppins (next/font, --font-poppins).
  Design tokens live in frontend/src/styles/tokens.css (light + .dark).
  EVERY page must have its own co-located `page.module.css` (Next CSS
  Modules); reusable components have their own `*.module.css`. Global CSS
  holds only tokens + base body rules. Components use CSS variables, not
  raw hex. Tailwind stays available for utility/nested layout.

8. DATA MODEL & API (current)
------------------------------------------------------------------------
Models implemented:
  User    : fullName, email(unique), passwordHash(select:false),
            avatarUrl, avatarPublicId, jobTitle, department, presence,
            statusMessage, theme, role, isDisabled, disabledAt,
            lastLoginAt, passwordChangedAt, passwordResetTokenHash,
            passwordResetExpiresAt, timestamps.
  Session : user(ref), activeOrganization(ref Organization), tokenHash(unique),
            userAgent, ipAddress, expiresAt (TTL), revokedAt, timestamps.
  Organization       : name, slug(unique), logoUrl, logoPublicId, settings
                       (allowMemberChannelCreation, defaultChannelType),
                       status(ACTIVE/ARCHIVED), timestamps.
  OrganizationMember : organization(ref), user(ref), role(ORG_ROLES),
                       status(ACTIVE/DISABLED), joinedAt; unique
                       (organization,user).
  Invitation         : organization(ref), email, role, tokenHash, invitedBy,
                       status(PENDING/ACCEPTED/REVOKED), expiresAt; timestamps.
  Channel            : organization(ref), name, topic, purpose,
                       type(PUBLIC/PRIVATE), createdBy(ref User),
                       status(ACTIVE/ARCHIVED); unique (organization,name).
  ChannelMember      : organization(ref), channel(ref), user(ref),
                       role(MODERATOR/MEMBER),
                       notifyPreference(ALL/MENTIONS/MUTE),
                       status(ACTIVE/REMOVED), joinedAt, lastReadAt;
                       unique (channel,user). Removal sets REMOVED (not
                       delete) so the channel stays hidden/denied for that
                       user; admins can re-add (reactivates).
  Conversation       : organization(ref), type(DIRECT/GROUP),
                       participants[{user(ref), joinedAt, lastReadAt}],
                       directKey(unique sparse "<org>:<sorted user ids>"
                       -> 1:1 dedupe), groupKey(unique sparse, same format,
                       -> exact-set group dedupe), createdBy(ref User),
                       lastActivityAt.
  Message            : organization(ref), channel(ref) XOR conversation(ref),
                       sender(ref User), content(max 4000; optional when the
                       message carries attachments, validated in the service),
                       parentMessageId(ref Message|null; flat thread ->
                       the ROOT id), alsoSentToChannel(bool), replyCount,
                       lastReplyAt, replyUserIds[] (denormalized on the root),
                       mentionedUserIds[](ref User), mentionAll(bool),
                       mentionHere(bool), editedAt, deletedAt; timestamps.
                       Mentions are parsed from content tokens <@id>/<!channel>/
                       <!here> (utils/mentions.js) + filtered to members;
                       @channel/@here gated to channel moderators/org admins.
                       Serializable message exposes mentions[{id,fullName}],
                       mentionAll, mentionHere and attachments[].
  ThreadFollow       : organization(ref), threadRoot(ref Message),
                       user(ref), lastReadAt; unique (threadRoot,user).
  Reaction           : organization(ref), message(ref), user(ref), emoji;
                       unique (message,user,emoji). Messages serialize a
                       reactions[] ({emoji,count,users,reactedByMe}).
  Attachment         : organization(ref), message(ref), channel(ref|null) XOR
                       conversation(ref|null) (denormalized for the media
                       browser), uploader(ref User), kind (IMAGE/VIDEO/AUDIO/
                       FILE), url, publicId, resourceType, format, bytes,
                       originalName, mimeType, width, height, duration;
                       timestamps. Stored from a Cloudinary signed DIRECT
                       upload (folder org/<orgId>/attachments, resource type
                       "auto"); files never live in MongoDB. Deleting a message
                       removes its Attachment rows and Cloudinary assets.
                       Serialized as attachments[] ({id,kind,url,publicId,
                       name,mimeType,bytes,width,height,duration,createdAt}).
  ChannelPin         : organization(ref), channel(ref), message(ref),
                       pinnedBy(ref User); unique (channel,message). Channel
                       pinned messages. Serialized with the pinned message.
  Bookmark           : organization(ref), user(ref), message(ref); unique
                       (user,message). Personal "saved items" (Save for later).
                       Deleting a message removes its pins and bookmarks.

10. SECURITY RULES (enforced since hardening step 1, 2026-10-10)
------------------------------------------------------------------------
Keep these invariants when adding features:
  - Uploads: the server signs uploads into fixed folders
    (utils/media.js avatarFolder(userId) = avatars/<userId>,
    attachmentFolder(orgId) = org/<orgId>/attachments). Any client-sent
    {url, publicId} goes through utils/attachments.assertOwnedAsset: the
    publicId must be inside the signed folder and the URL must point at
    that publicId. One attachment publicId = one message (duplicates are
    rejected), so deleting a message can only delete its own files. Old
    avatars are deleted only if inside the user's own avatar folder.
  - Channel writes (post, pin/unpin, edit, delete, react) need an ACTIVE
    channel membership AND a non-archived channel:
    middleware/channel.requireChannelWrite (routes) and
    messageService.assertCanWrite (message-level actions). Public channels
    stay readable without joining (Slack behaviour).
  - Org roles: only an OWNER may grant OWNER, invite an OWNER, or change /
    disable / remove an existing OWNER
    (organizationService.assertCanManageRole; invitation create checks
    actorRole). The Members UI hides those controls from admins.
  - Live access is cut when access is lost (sockets/kick.js):
    removed/disabled org member -> their sockets in that org disconnect;
    logout -> that session's sockets; password change -> every OTHER
    session is revoked + disconnected; password reset -> all. Leaving /
    being removed from a PRIVATE channel drops the user's sockets from
    channel:<id>. Socket handshake binds an org only while the user is an
    ACTIVE member of the session's active org; socket.data.sessionId is
    stored for targeted disconnects.
  - Huddles: WebRTC signals are relayed only between two ACTIVE
    participants of a LIVE huddle and only to the target user's sockets.
    Huddle leave-on-disconnect runs on `disconnecting` (socket.rooms is
    empty by `disconnect`) and skips users still in the huddle from
    another tab.
  - Auth: sign-up ignores a client `role`; unknown-email logins still run
    a scrypt verify (no timing leak); login picks the oldest ACTIVE
    membership; rate limits are per IP + per account email (login,
    reset), per user (password change), per IP (invite lookup).
    rateLimit({ key }) accepts a custom bucket function.
  - Frontend: ?next= redirects go through lib/redirect.safeNextPath
    (same-site paths only).
  Known open items (not done in step 1): attachment files are public
  Cloudinary URLs (anyone with the link can open them) and upload
  size/type limits are still only client-reported; CORS reflects any
  origin unless NODE_ENV=production; no CSRF token (SameSite=Lax only).

11. REALTIME & MESSAGING RULES (since step 2, 2026-10-10)
------------------------------------------------------------------------
  - Reconnects: Socket.IO gives a reconnected socket NO rooms. Every hook
    that joins a room also listens to 'connect' and re-emits its join,
    then resyncs (useMessages.resync merges the latest page into loaded
    history; useThread reloads). Switching workspace calls
    lib/socket.reconnectSocket() (OrgContext.switchOrg) because the server
    binds a socket to the session's active org at handshake.
  - History paging: useMessages exposes hasOlder / loadingOlder /
    loadOlder (cursor = oldest loaded _id, PAGE_SIZE 30 = server default).
    MessageList loads older when scrolled within 200px of the top (or via
    "Load older messages") and keeps the scroll position (layout effect
    on the first message id). New-message detection counts only messages
    appended after the previous newest id.
  - Stale responses: useMessages, ActiveChannelContext and
    ActiveConversationContext drop responses for a chat the user already
    left; workspaces show a spinner until the loaded item matches the
    route id. Socket message handlers ignore events whose channelId /
    conversationId is not the open chat.
  - Unread: unread.updated / notification.created carry organizationId;
    clients ignore other workspaces' events. When an unread.updated
    targets the chat currently open in a VISIBLE tab, UnreadContext marks
    it read on the server (debounced 800ms); becoming visible also marks
    the open chat read.
  - Presence lives in its own PresenceContext (hooks/usePresence); socket
    consumers no longer re-render on presence changes.
  - Typing: server broadcasts typing=false for every key a socket had on
    disconnect; clients also expire a typing entry after 7s.
  - Reactions: live broadcasts (message.updated, thread.updated) are
    serialized viewer-neutral (viewerId null); ReactionPill derives "mine"
    from reaction.users. Never broadcast a payload serialized for the
    actor.
  - Edits/deletes/reactions are emitted to the chat room AND
    thread:<rootId> (emitToMessageRooms).
  - Delete rules: authors delete their own; channel moderators and org
    OWNER/ADMIN may delete anyone's CHANNEL message (not DMs); UI shows
    "Delete message" via MessageList/ConversationView canModerate.
    Deleted messages cannot be edited/reacted (404). Deleting a reply
    recomputes the root's replyCount / replyUserIds / lastReplyAt
    (messageService.refreshThreadStats) and emits thread.updated. A
    deleted ROOT with replies stays listed as a placeholder ("This
    message was deleted.", replies still reachable); it disappears when
    its last reply is deleted.
  - Threads: replying auto-follows the replier; the root author is
    auto-followed on the first reply. Followers who are no longer channel
    members get no thread notifications.
  - Group DMs: "Add people" never changes an existing DM. It finds or
    creates the group DM for the combined people (Slack) and the UI
    navigates there; earlier history is not shared.
  - Channel rename/topic/purpose/archive emit channel.updated to org:<id>
    (public) or each member's user room (private); the open
    ChannelWorkspace reloads its header on it.
  - Message indexes: {channel,_id}, {conversation,_id},
    {parentMessageId,_id} for cursor paging.
  - Deep links: FocusMessageContext re-reads ?message= on every pathname
    change (and clears focus otherwise); Activity items also call
    focusMessage on click. MessageList handles each focus request once.
