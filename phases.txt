========================================================================
SMALL ORGANIZATION COMMUNICATION & COLLABORATION PLATFORM
IMPLEMENTATION PHASES
========================================================================

Version      : 2.0
Target       : All in-scope features at Slack-parity behavior
               + MULTI-ORGANIZATION (multi-tenancy)
Stack        : Next.js (frontend) | Node.js + Express (backend, JavaScript)
               MongoDB + Mongoose | Cloudinary | Socket.IO (in-memory)
               No Redis
Source Spec  : project.md (SRS v1.2, see sections 59-60)
========================================================================

------------------------------------------------------------------------
HOW TO READ THIS PLAN
------------------------------------------------------------------------
Each phase lists:
  - Goal        : what the phase delivers
  - Slack parity: the behaviors that make this feature "Slack-like"
  - Tasks       : concrete work items
  - Deliverable : what is demonstrably working at the end
  - Depends on  : prerequisites

Conventions (operator rules): keep files small and reusable; no test
scripts; no dependency installation by the AI; backend is JavaScript;
every backend update also updates memory.txt and till.txt.

PHASE 1 - AUTHENTICATION, PROFILES & PRESENCE FIELDS  [DONE]
========================================================================
Goal
  Secure sessions and editable profiles.

Slack parity
  - Profile: full name, email, image, job title, department, presence,
    status emoji + status message with optional clear-after.
  - Presence values ACTIVE / AWAY / DND / OFFLINE (field added now,
    driven by Socket.IO in Phase 4).
  - Session management and password change as Slack-like account settings.

Delivered
  - scrypt hashing, signed HttpOnly cookie sessions, register-first-admin,
    login/logout, password reset/change, profile + Cloudinary avatar.
  - Phase 1 auth UI (login/register/forgot/reset) with per-page CSS.

Note (multi-tenancy)
  - Users are global identities; organization membership arrives in
    Phase 2. Session will carry an `activeOrganizationId`.

========================================================================
PHASE 2 - ORGANIZATIONS, MULTI-TENANCY, ROLES & USER MANAGEMENT
========================================================================
Goal
  Full multi-organization support with per-org roles and tenant isolation.

Slack parity
  - Workspace switcher; a user can belong to several organizations.
  - Create organization (self-serve onboarding) + invite members.
  - Roles per organization: Owner, Admin, Moderator, Member.
  - Admin can invite/disable/reactivate/remove and assign roles.

Tasks
  [ ] Models: Organization (name, slug, logo, settings, status),
      OrganizationMember (user, organization, role, status, joinedAt).
  [ ] Add `organizationId` to every tenant-owned model and enforce it in
      every service query/mutation (tenant isolation).
  [ ] Session: store and resolve `activeOrganizationId`; default to the
      user's first membership.
  [ ] Middleware: `requireOrganization` (resolve active org + membership)
      and `requireOrgRole(...)` (replaces ad-hoc role checks).
  [ ] Endpoints:
        POST   /organizations                 (create)
        GET    /organizations                 (mine)
        GET    /organizations/:id
        PATCH  /organizations/:id
        POST   /organizations/:id/switch
        POST   /organizations/:id/invitations
        GET    /organizations/:id/members
        PATCH  /organizations/:id/members/:userId
  [ ] Invitations: token-based invite + accept flow.
  [ ] Onboarding route for users with no membership.
  [ ] Slug uniqueness + org settings defaults.

Deliverable
  Users create/join/switch organizations; all data isolated per org;
  admins manage members and roles within their org only.

Depends on
  Phase 1.

PHASE 4 - MESSAGING, DMS & REAL-TIME
========================================================================
Goal
  Real-time channel messaging plus 1:1 and group DMs.

Slack parity
  - Message list grouped by author/time; full timestamp; edited marker.
  - 1:1 and group direct messages (3+ participants).
  - Typing indicators and presence (ACTIVE/AWAY/DND/OFFLINE).
  - Unread divider ("new messages since…").

Tasks
  [ ] Models: Conversation (org, type DIRECT/GROUP, participants,
      lastActivity), Message (org, channel|conversation, sender, content,
      parentMessageId, timestamps).
  [ ] Endpoints:
        GET/POST /channels/:id/messages
        GET      /conversations
        POST     /conversations
        GET      /conversations/:id/messages
  [ ] Socket.IO: authenticate, join per-org/user rooms, emit:
        message.created/updated/deleted, typing.updated, presence.updated,
        notification.created, channel.updated, thread.updated
  [ ] In-memory presence (with DND) and typing with expiry.
  [ ] All events scoped to active organization.

Deliverable
  Users chat in channels and DMs in real time with presence/typing.

Depends on
  Phase 3.

PHASE 5 - MESSAGE ACTIONS, THREADS, REACTIONS, MENTIONS, FILES
========================================================================
Goal
  Slack-like message interactions.

Slack parity
  - Hover actions: edit, delete, copy link, pin, save, reply in thread.
  - Thread panel: parent + replies, reply count, also-send-to-channel,

  - Reactions with counts and "who reacted".
  - Mentions @user/@channel/@here with autocomplete + highlight.
  - Files: size/MIME/extension validation, previews, download, media grid.

Tasks
  [ ] Edit/delete: PATCH/DELETE /messages/:id (+ edited marker, audit).
  [ ] Threads: GET /messages/:id/thread; reply via parentMessageId;
      thread follow model; also-send-to-channel.
  [ ] Reactions: POST/DELETE /messages/:id/reactions; counts.
  [ ] Mentions: parser for @user/@channel/@here + notification hooks.
  [ ] Pins: POST/DELETE /channels/:id/pins; pin list.
  [ ] Saved items: POST/DELETE /bookmarks (personal).
  [ ] Attachments: Attachment model; Cloudinary signed upload; metadata.
  [ ] Media browser data for the context panel.

Deliverable
  Messages can be edited/deleted/threaded/reacted/mentioned/pinned/saved
  and carry Cloudinary files.

Depends on
  Phase 4.

  [ ] Models: Notification, Bookmark(saved), Draft.
  [ ] Endpoints: GET /notifications, PATCH /notifications/:id/read,

  [ ] Unread tracking per channel/DM/notification; real-time updates.
  [ ] MongoDB text indexes scoped by organization + access.
  [ ] DND/snooze preference on the user; queue notifications during DND.
  [ ] Theme preference per user (light/dark/system).

Deliverable
  Notifications, unread, search, drafts and DND behave like Slack.

Depends on
  Phase 5.

PHASE 6.6 - HUDDLES (AUDIO / VIDEO / SCREEN SHARE)  [DONE]
========================================================================
Goal
  Slack-style huddles inside channels and DMs (1:1 + group).

Slack parity
  - Start a huddle from a channel or DM (headphone button in header).
  - Join / leave; a live-huddle pill on sidebar rows; Join bar in-channel.
  - Mic / camera / screen-share toggles; auto-end when the last of person
    leaves; only the starter can end it for everyone.
  - One live huddle per conversation; "Huddle ended · 3 min" chat card
    posted to the transcript.

Architecture
  - Signaling over the existing Socket.IO (rooms `huddle:<id>`, relay
    `huddle:signal` offer/answer/ICE; `huddle:media` media states).
  - WebRTC P2P mesh client-side (no SFU); free Google STUN + optional
    TURN via NEXT_PUBLIC_TURN_URL. <= 8 participants recommended.
  - REST: POST /huddles, GET /huddles/active, GET /huddles/history,
    POST /huddles/:id/{join,leave,end}.
  - Models: Huddle; Message.huddle links the ended-huddle card.

Out of MVP
  - SFU (large calls), video tiles > 8, thread huddles, recording,
    captions, DND-aware "huddle started" notifications (land with 6.3).

Deliverable
  Working audio/video/screen-share huddles; summary card in chat.

Depends on
  Phase 6.5 (drafts) - intentionally slotted after it in the roadmap.
